# CLAUDE.md: правила работы над «Автодневником»

## Источник истины
Требования описаны в `docs/`. Перед любой работой прочитай их в этом порядке:
1. `docs/01-vision.md`
2. `docs/08-roadmap.md` и `docs/progress.md`: какой этап текущий
3. `docs/02-requirements.md`, `docs/03-user-stories.md`: требования текущего этапа
4. `docs/04-domain-model.md`, `docs/05-bot-ux.md`, `docs/06-nfr.md`, `docs/07-stack.md`
5. `docs/decisions.md`: уже принятые решения

## Порядок работы
- Работай строго над одним этапом из `08-roadmap.md`. Функции будущих этапов не реализуй, даже частично. Допустимы только точки расширения, без которых нельзя обойтись.
- В начале этапа выдай короткий план: что будет сделано, какие требования (FR/US) закрываются, какие вопросы есть. Дождись подтверждения владельца.
- Если документы противоречат друг другу, что-то не описано или пришлось выбирать вариант, не додумывай. Задай вопрос, а принятое решение запиши в `docs/decisions.md`.
- Мелкие коммиты с понятными сообщениями. Каждый коммит оставляет проект в рабочем состоянии.

## Качество
- Бизнес-правила из `04-domain-model.md` и расчёт напоминаний покрываются автотестами.
- Перед завершением этапа прогони линтер и тесты. Результаты приведи в отчёте как есть, без пересказа.
- Схема БД меняется только миграциями. Существующие данные не ломаются.
- Тексты и поведение бота соответствуют `05-bot-ux.md`.
- Новая зависимость допускается только с обоснованием в `decisions.md`.

## Безопасность
- Не коммить токены, ID, `.env` и данные (БД, фото, бэкапы). Проверяй `.gitignore`.
- Не выполняй на VPS разрушительных действий (удаление данных, перезапись БД) без явного подтверждения владельца.

## Завершение этапа
1. Обнови `docs/progress.md`: статус, что сделано, отклонения от документов.
2. Отчёт владельцу: что сделано, как проверить вручную (шаги в Telegram по критериям этапа), результаты тестов и линтера, открытые вопросы.
3. Следующий этап начинай только после подтверждения владельца.

## Команды (Windows, из корня проекта)
- Установка: `python -m venv .venv; .\.venv\Scripts\python -m pip install -e ".[dev]"`
- Запуск: `.\.venv\Scripts\python -m bot` (применяет миграции; нужен `.env`, см. `.env.example`)
- Тесты: `.\.venv\Scripts\python -m pytest`
- Линтер: `.\.venv\Scripts\ruff check .`
- Новая миграция: `.\.venv\Scripts\alembic revision --autogenerate -m "..."` (берёт `DATA_DIR`)
- Тесты на Python 3.12 в Docker: `docker build --target test .`

## Структура
- `bot/services/` — логика. Чистые, с юнит-тестами (`tests/test_rules.py`): `parse` (форматы ввода), `mileage` (правила пробега), `dates`. С БД: `profiles` (машины и показания), `deployments` (версии).
- `bot/handlers/` — Telegram: `profile_form` (мастер профиля), `cars`, `mileage`, `settings`, `start`; `common` — `ANSWER`, `send_menu`, `show`. `bot/views.py` — все тексты; `bot/keyboards/` — кнопки и callback-данные.
- `bot/fsm.py` — состояние диалогов в SQLite (в транзакции апдейта).
- `bot/scheduler.py` — цикл раз в 60 с: уведомления о версиях (напоминания — этап 6).
- Диалоговые тесты: `tests/test_flows.py`, `tests/test_stage1.py` через `tests/harness.py` (фейковый Telegram, управляемые часы, `press("текст кнопки")`, `add_car`).

## Соглашения
- Время только через `bot.clock.utcnow()`; в SQLite хранится UTC (`as_utc`).
- Записи в БД — под общим `db_lock` (хэндлеры и планировщик).
- Сообщения в Telegram HTML; пользовательский и внешний текст экранировать `html.escape`.
- Текстовые ответы в шагах диалога ловить фильтром `ANSWER`: команды и кнопки меню выходят из сценария.
- Даты показаний — локальная дата владельца (`common.today`), не UTC.

## Деплой
push в main → GitHub Actions (тесты в Docker) → образ `ghcr.io/two-lifes/auto_tracker` →
SSH → `deploy/deploy.sh` в `/opt/auto_tracker` (копия БД, ожидание "Run polling", откат при ошибке).
На сервере: `.env`, `data/`, `backups/`, `.deployed_tag`. Деплой выключен, пока нет переменной
репозитория `DEPLOY_ENABLED=true`.
